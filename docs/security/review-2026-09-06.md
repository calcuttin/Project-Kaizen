# Public-release and account-isolation review — 2026-09-06

The reviewed application and backend fixes are deployed. Repository privacy remains enabled; changing its visibility is a separate release decision. Clerk stays on its current development instance at the user's request until a custom domain is available. This review provides evidence for the tested account boundaries, not a guarantee against every vulnerability.

## Findings and deployed fixes

| Finding | Resolution |
| --- | --- |
| Accounts shared browser storage keys. | Every persisted module, preference, repository, queue, conflict record, and sync cursor is account-scoped. The workspace waits for authenticated hydration. Identity changes lock writes and reload the document. |
| Requests and pending sync could complete under a different session. | Token providers and requests are bound to the originating Clerk session. Stopped sync is aborted, late responses are ignored, and asynchronous storage operations capture their owner. |
| The sample-data dialog reopened on login. | Removed automatic onboarding. Signed-in accounts open their saved workspace; sample data remains an explicit Settings action. |
| Personal bookshelf/Notion fixtures and screenshots were committed and bundled publicly. | Source fixtures are empty, personal Studio defaults are removed, and production/cloud builds cannot enable bundled imports. Original data and 14 screenshots are preserved under ignored `private-data/pre-public-review/`. |
| A force push left old private objects retrievable by commit ID on GitHub. | Created a separate clean repository at the original `calcuttin/Project-Kaizen` address. The original repository is retained as a private archive. The old commit was not found in the clean repository; a fresh clone's history privacy scan passed. Do not publish the archive. |
| Old Vercel deployments retained personal JavaScript bundles. | Removed all nine deployments preceding the security release. The checked old deployment URLs return 404. The current production import chunk is 627 bytes and contains no bundled personal collection. |
| Anonymous callers retained direct EXECUTE grants on sync/profile RPCs. | Revoked PUBLIC and anon grants for all three functions, preserving authenticated access. Applied live and recorded in migration `202609060003_restrict_anonymous_rpc.sql`. |
| React Router had two moderate dependency advisories. | Upgraded to patched 7.x; the subsequent dependency audit reported zero known vulnerabilities. |
| Database CI used stale JWT claims and a stale migration fingerprint. | Corrected claims to `request.jwt.claims`, expanded ownership tests, and updated the fingerprint. All 87 database assertions passed in GitHub CI. |
| Service worker caching was too broad. | Cache only public shell/static asset paths, skip authenticated requests and API/auth paths, and rotate the cache version. |
| Automatic online covers disclosed reading metadata to third parties. | Online covers default off per account, with an explicit Settings → Privacy choice and disclosure. Manual ISBN lookup remains an explicit external request. |
| Account deletion ignored storage failures and incomplete file listings. | The deployed function removes every page and nested folder, fails on storage errors, uses generic errors, and verifies Clerk tokens itself. Client sync stops before deletion. Two disposable accounts were deleted successfully in live tests. |
| Imported links could use executable schemes; framing protection was missing. | Feed links permit only HTTP(S); production responds with anti-framing CSP and `X-Frame-Options: DENY`. |

## Live evidence

Production database metadata verified:

- All **24 public application tables** have RLS enabled, with authenticated policies requiring `owner_id = auth.jwt() ->> 'sub'` for both access and writes.
- `ensure_profile`, `push_changes`, and `pull_changes` run as the invoking user. Their deployed bodies match the reviewed Clerk migration.
- The `import-artifacts` bucket is private; object access and uploads require the authenticated subject's folder prefix.
- Anonymous callers cannot execute any of the three RPCs; authenticated callers retain access.

A rollback-only test using simulated A/B JWT claims passed read/insert/update/delete isolation across **21 entity tables**. The user ran the prepared SQL and its PASS result was inspected; all synthetic rows were rolled back.

A subsequent live test used **two disposable Clerk development users with real Clerk-issued session tokens**, the hosted app's public Supabase key, and the deployed backend:

- B could not read A's records, insert as A, update A, or delete A across all 21 entity tables.
- Both accounts used the same sync entity ID independently. Caller-supplied ownership could not redirect a mutation to the other account; each pull returned only its own change.
- B could not download A's private file or upload into A's folder.
- Deleting A through the deployed Edge Function removed A's rows and nested files while preserving B's book and file.
- Deleting B then removed its test workspace. Both disposable users and their workspaces were removed; no existing user account was used for destructive testing.
- An unauthenticated request to account deletion returned HTTP 401.

The user signed in at the stable production address and confirmed the saved import loads. The inspected application showed the workspace as synced.

## Validation

- TypeScript, schema fingerprint, source scan, production build, and both GitHub CI jobs passed for the security implementation.
- **23 unit tests** cover storage/session isolation, delayed operations, repositories, unsafe links, storage cleanup, and existing behavior.
- **5 device browser tests** cover imports, backups, and reopening saved records.
- **1 cloud browser test** uses the real application with synthetic Clerk/Supabase transports to test import, reload, account switching, sign-out, and return to the original account.
- **87 pgTAP assertions** passed in GitHub CI, including all entity policies, sync ownership, RPC grants, and storage policies.
- The live real-token checks above additionally exercise Clerk-to-Supabase trust and account deletion. They are API integration tests, not a two-person browser login exercise.
- Targeted source/history scans found no matching secret-token/private-key/JWT patterns in the clean publication history. These scans do not replace a comprehensive secret-detection review.

## Preservation and future production setup

The pre-rollout workspace export is valid JSON and retained under ignored `private-data/rollout-backup/`, along with a verified Git bundle of the original history and the original changes. The old GitHub repository remains a private archive. These backups contain private material and must never be committed, deployed, or published.

The new account caches intentionally do not adopt the legacy shared browser cache or pending queues, because their owner cannot be established safely. Existing cloud records replay from sequence zero. If unsynced legacy records need recovery, import the verified backup while signed into the correct owner account.

The user explicitly deferred Clerk production setup because no domain is owned yet. Before a public production launch, configure the production Clerk instance and matching Supabase trust, preserve validated identity/owner mappings if user IDs change, and verify production login and redirects. Do not switch publishable keys alone.

## Boundaries

Account separation is logical isolation, not browser-storage encryption. Someone with access to the same OS/browser profile or DevTools can inspect cached workspaces. Separate browser profiles are appropriate on shared machines.

Data is readable by authorized service operators; it is not end-to-end encrypted. This review did not audit provider backups, all operator permissions, abuse/rate limits, or artwork licensing. Deleting old deployments cannot recall copies already downloaded or retained by external caches. Existing AGPL licensing and artwork provenance records remain; no legal clearance is asserted.
