# Public-release and account-isolation review — 2026-09-06

**Release decision: keep the repository private until the outstanding rollout steps below are complete.** This review found and fixed application isolation defects, verified the deployed database policies, and identified personal material already present in public web assets. It is not a guarantee against all security vulnerabilities.

## Findings and changes

| Priority | Finding | Resolution/status |
| --- | --- | --- |

Signing into another account on the same browser could expose the previous workspace. | Local fix: separate account keys for every persisted module, preferences, and repository. ## Live database evidence

A read-only metadata query against the production project verified:

- All **24 public application tables** have RLS enabled.
- Each has exactly one policy for the authenticated role with both USING and WITH CHECK equal to `owner_id = auth.jwt() ->> 'sub'`.
- `ensure_profile`, `push_changes`, and `pull_changes` run as the invoking user, not as security definers.
- The deployed function bodies match the reviewed Clerk migration (body hashes compared locally).
- `import-artifacts` is private. Read/insert/delete policies restrict paths to the authenticated subject's folder.
- After hardening, anonymous users cannot execute any of the three RPC functions; authenticated users retain execution rights.

A separate rollback-only production test of synthetic A/B records across **21 entity tables passed**. The user ran the prepared query, and the SQL Editor result was inspected afterward: `PASS: read/insert/update/delete isolation across 21 entity tables; all synthetic data rolled back`. The test verified that B cannot read A's synthetic rows, insert rows owned by A, or update/delete A's rows. Its transaction ends with ROLLBACK. This tests database policies using simulated authenticated JWT claims; it does not replace a full login test with two real Clerk accounts. No private user rows were read during the metadata inspection.

## Validation

- TypeScript check, unit tests, schema fingerprint, targeted public-source scan, and production build pass.
- **23 unit tests** cover storage isolation, delayed queue reads, late responses, session-bound tokens, repository isolation, unsafe URLs, storage deletion, and existing behavior.
- **5 device browser tests** cover imports, backups, and reopening saved records.
- **1 cloud browser test** runs the real application with synthetic Clerk and Supabase transports: A imports a book, reloads, switches to B, checks B cannot see/upload A's book or import history, signs out, then returns to A.
- Registry dependency audit after upgrading reports **zero known vulnerabilities**.
- Targeted scans of all 8 local commits found no matching secret-token/private-key/JWT patterns. A database URL match was a documented password placeholder. This is a targeted scan, not a comprehensive secret-detection guarantee.
- The history privacy scan still fails as expected because historical personal fixtures/screenshots remain reachable.
- The rollback-only production database isolation test passed across 21 entity tables. The separate full pgTAP suite still requires execution with Supabase/Postgres; Docker is unavailable locally. The production Edge Function was not invoked for destructive account-deletion testing.

## Rollout checklist

1. **Back up the existing workspace before deploying.** Export from the old app through Settings → Export. The new code intentionally does not assign the shared legacy browser cache or legacy pending queues to whichever account signs in first. Existing cloud records replay from sequence zero into the new account cache. Unsynced records must be restored from a verified backup while signed into their owner's account.
2. Review and push the frontend changes to the private GitHub repository, allowing Vercel to deploy them. These working-tree changes have not been committed or pushed by this review.
3. Deploy both `index.ts` and `storage.ts` for the updated `delete-account` function. The handler verifies Clerk tokens itself; its config disables Supabase's incompatible legacy JWT check. The RPC grant migration was already applied manually to production.
4. **Deferred by user choice (2026-09-06):** keep the current Clerk development instance until a domain is available. Before public production use, replace it with a production instance and matching Supabase trust configuration. Plan identity/data migration: development and production Clerk user IDs may differ. Preserve owner mappings before switching. Verify allowed origins, redirects, and production login in staging first.
5. Remove personal files from **all Git history** before making the repo public, or publish a clean repository history. Paths include both `src/data` fixture files and the archived PNGs under `design/library/`. Old Studio defaults also contain a personal publication URL. Do not rewrite/force-push existing history without an approved plan and a private backup.
6. Restrict or remove old Vercel deployments that contain personal bundles. Updating the primary deployment does not by itself remove older deployment URLs, already downloaded copies, browser caches, or external caches.
7. Run the corrected database suite and a production/staging two-account login test before inviting users. Verify backend and frontend changes are actually deployed; a local test pass is not deployment evidence.

## Boundaries and remaining limitations

Logical account isolation does not encrypt browser storage. Someone with access to the same OS/browser profile or DevTools can inspect IndexedDB, including caches of previously used accounts. Use separate browser profiles on shared machines. Signed-in offline use also depends on authentication state being available; this is not an offline authentication guarantee.

The server stores readable user data protected by RLS; it is not end-to-end encrypted against the service operator. This review did not audit cloud backups, operator privileges, abuse/rate limits, provider dashboards beyond the verified settings, or execute account deletion against a real user. The existing AGPL license and artwork provenance records are present; no legal clearance is asserted.
